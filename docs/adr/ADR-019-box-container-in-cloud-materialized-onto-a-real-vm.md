# ADR-019: Бокс — контейнер в облаке, кристаллизация — материализация на настоящую VM

## Статус

Принят 2026-07-30. **Отменяет ADR-016 и ADR-017.**

## Что было неверно

ADR-016 и смежные планы содержали две ошибки, обе фактические, а не вкусовые.

**1. Никакого парка gVisor нет и не планируется.** ADR-016 исходил из выделенного парка
Beget VM, на каждой из которых боксы запускаются песочницами `runsc`. Такого парка не
существует. Решение опиралось на инфраструктуру, которой нет, — то есть на предположение,
выданное за факт.

**2. Контейнер на VM — это не VM.** ADR-016 определял кристаллизованный артефакт как
«тот же OCI-образ и те же тома, запущенные как compose-сервис на выделенной Beget VM под
Portainer». Это контейнер, который живёт на виртуальной машине, а не виртуальная машина.
Обещание продукта — постоянная VM, которой владеет клиент, и compose-стек его не выполняет.

## Проверенное ограничение подложки

`portainer-agent/internal/terraform/templates/main.tf.tmpl` создаёт инстанс так:

```hcl
data "beget_software" "os" { slug = var.software_slug }   # напр. ubuntu-24-04

resource "beget_compute_instance" "app_server" {
  image = { software = { id = data.beget_software.os.id } }
}
```

Провайдер принимает **идентификатор ОС, разрешённый из слага**. Ни импорта своего образа
диска, ни загрузки из снапшота в этой поверхности нет (`grep` по
`snapshot|custom_image|image_id` в каталоге terraform не даёт ничего).

Следствие, и оно закрывает одну из двух возможных механик: **путь «собрать из контейнера
загружаемый образ диска и импортировать его в Beget» на этой подложке недоступен.** Не
«хрупок», а недоступен — провайдеру некуда передать образ.

## Решение

**1. Эфемерный бокс — контейнер в уже существующем облаке.** Никакого нового парка VM,
никакого gVisor, никакого своего железа. Бокс запускается там, где у нас уже есть
вычисления.

**2. Кристаллизация поднимает настоящую VM из стандартного слага и материализует бокс на
неё.** Пользовательская часть контейнера накатывается на файловую систему VM; **ядро, init и
загрузчик остаются собственными у VM.** Результат работает под systemd. В кристаллизованном
артефакте нет ни Docker, ни compose, ни агента Portainer.

**3. Жёсткое ограничение, вытекающее из (2): тёплый образ бокса и слаг VM обязаны быть одним
дистрибутивом одной версии** (сегодня `ubuntu-24-04`). Материализация userland одного
дистрибутива на ядро другого даёт химеру, которая соберётся и потом сломается в проде.
Это ограничение — часть механизма, а не рекомендация: сборка образа бокса должна падать,
если его база разошлась со слагом.

## Механизм материализации

Детерминированный, модели в пути нет. Это классический C2V, а не вывод описания.

1. **Заморозить бокс.** Дальше он источник истины и остаётся целым до точки фиксации.
2. **Определить множество userland:** файловая система контейнера **за вычетом** того, что
   принадлежит машине, а не приложению: `/proc`, `/sys`, `/dev`, `/run`, `/tmp`, `/boot`,
   `/lib/modules`, `/etc/fstab`, `/etc/machine-id`, `/etc/hostname`, `/etc/resolv.conf`,
   `/etc/hosts` и точки монтирования томов. Список фиксирован и **печатается в отчёте
   верификации** — иначе он тихо разойдётся с реальностью.
3. **Накатить его на `/` виртуальной машины** (rsync с сохранением прав, xattr и hardlink).
   Ядро и загрузчик VM не трогаются.
4. **Восстановить именованные тома** каталогами по их путям монтирования.
5. **Записать env** в `/etc/dada/box.env`, `chmod 600`, владелец root, **по SSH, не через
   git**. Юнит ссылается на файл через `EnvironmentFile`. Значения в коммит не попадают
   никогда.
6. **Перевести entrypoint и порты в systemd-юнит:** `ExecStart` из entrypoint и cmd,
   `WorkingDirectory` из рабочего каталога контейнера, `EnvironmentFile`, `Restart=always`.
   Публикуемые порты переобъявляются как есть.
7. **Верифицировать:** равенство манифеста файлов `(path, size, mode, sha256)` с обеих сторон;
   равенство множества слушающих сокетов; HTTPS-проба снаружи платформы; настоящий `SELECT 1`
   по `DATABASE_URL` и `HEAD` по бакету **изнутри** VM. Не «rsync вернул 0».

Что честно **не** переезжает: состояние в памяти, `/tmp`, и запущенные процессы без
перезапуска. Процессы перезапускаются один раз, теми же командами, с тем же окружением.
Формулировка на лендинге уже приведена в соответствие.

## Последствия

### Изоляция становится открытым вопросом, и это блокер

Это главная цена решения, и её нельзя замазать. На управляемом Kubernetes нельзя добавить
RuntimeClass, поэтому под бокса **делит ядро с узлом**. Раньше эту проблему закрывал gVisor,
которого нет.

Доступные средства, все k8s-нативные: **отдельный пул узлов только под боксы** с taint и
toleration, Pod Security Standards в профиле `restricted`, `seccomp: RuntimeDefault`, сброс
всех capabilities, `NetworkPolicy` с egress по умолчанию запрещённым, лимиты
`ephemeral-storage`, `ResourceQuota` и `LimitRange`, user namespaces если версия кластера их
даёт.

**Не проверено и должно быть проверено до любого публичного доступа:** даёт ли управляемый
Kubernetes Beget отдельный пул узлов с taint. Если не даёт, боксы делят ядро с control plane
платформы, и это неприемлемо — тогда подложку для эфемерной части надо выбирать заново.

### Обещание «бокс с рутом» требует решения

Контейнер без песочницы на общем узле — ровно тот случай, когда настоящий root выдавать
нельзя. Варианты:

- **пул узлов только под боксы**: root внутри user namespace, ядро делится только с другими
  боксами, но не с платформой. Рекомендуемый;
- **бокс без root**: тогда меняется копирайт на лендинге, а не архитектура.

Решение принимается до открытия доступа. До него формулировка про root на лендинге —
необеспеченное обещание.

### Docker внутри бокса надо доказать заново

Без `privileged` в поде это rootless BuildKit с fuse-overlayfs. Возможно, но обязано быть
подтверждено прогоном настоящего `docker build`. Если не подтвердится — обещание переписывается
до публикации, а не после.

### Кристаллизованная VM выходит из парка Portainer

Она не хост контейнеров, поэтому управлять ею через Portainer нечем. Существующий путь
`create_appserver.go` → `bootstrap.sh.tmpl` ставит `docker.io` и агент Portainer с
монтированием `/var/run/docker.sock` и `/:/host` — для кристаллизации он **не применяется**.
Нужен свой bootstrap: базовая ОС, sshd, systemd, без Docker и без агента.

Именно этот вывод частично наследуется от ADR-017, но по другой причине: не потому, что на
хосте чужой код, а потому, что кристаллизованный артефакт вообще не контейнерный хост.

### Что это даёт

Ни нового парка, ни gVisor, ни капитальных затрат. Эфемерная часть работает на
инфраструктуре, которая уже есть. А кристаллизованный артефакт — настоящая виртуальная машина
с собственным ядром и systemd, которой владеет клиент, а не контейнер, притворяющийся ею.

## Что осталось верным из отменённых ADR

- Кристаллизация — **механический перенос объекта, а не вывод описания моделью**. Причина, по
  которой pty-версия была убита (`curl | bash` — одна строка в записи и сотни изменений в
  системе), в силе: мы владеем файловой системой, которую он произвёл, и переносим её, а не
  угадываем.
- Точка фиксации, матрица отказов, дисциплина лимитов Let's Encrypt и порядок «верификация
  раньше переноса данных» — переносятся без изменений.
- Обещания лендинга, которые архитектура не держит, переписываются **до** публикации.
