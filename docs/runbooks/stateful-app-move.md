# Stateful app move operator runbook (dbmove)

How to move a stateful, non-dada-managed app across projects/namespaces on
beget-prod using the `dbmove` tool (`tools/dbmove/`), without losing DB data,
volume data, or app secrets. Covers the two proven moves: `n8n`
(example-project -> platform) and `telemost-bot` (example-project -> internal).

Background: `docs/adr/ADR-014-move-app-across-projects.md`,
`tasks/move-app-phase1-spec.md`, `tasks/move-app-phase2-3-spec.md` (ground
truth verified on prod 2026-07-23). This doc is the human-facing wrapper
around the tool; read it before running anything with `--execute`.

## 1. Purpose and safety model

`n8n` and `telemost-bot` are not dada-managed `App` CRs - they are plain Argo
Applications generated by the `tenant-apps` ApplicationSet from a directory
generator over `clusters/beget-prod/projects/*/environments/*/apps/*/` in
argo-infra. Moving them is a git-folder relocation, not a platform MoveApp
operation. `dbmove` is a small Go CLI that performs that relocation plus the
supporting DB/volume/secret steps as an explicit, dry-run-first plan.

The whole design is non-destructive:

- **DB stays put; only the route to it changes.** Every ServiceDatabaseV2 is a
  logical database inside the ONE shared Postgres (`postgresql.databases.svc.cluster.local`,
  StatefulSet `postgresql` in ns `databases`). The Crossplane `Database` MR is
  `deletionPolicy: Orphan`. The chart renders `spec.namespace: {{ .Release.Namespace }}`,
  so moving the app's folder (below) is what re-points the namespace - Crossplane
  redelivers the `<app>-db-credentials` secret into the target namespace, and
  `Orphan` means the CR change can never drop the underlying logical database.
  There is no dump/restore and no rename in this path; it is a re-point. Both
  source and target namespaces can reach the same DB with the same
  credentials during cutover - no split-brain.
- **Volumes are copied, never surgically reattached.** Source PVCs are
  Longhorn with `reclaimPolicy: Retain`. `dbmove` backs up each source volume
  and restores that backup into a **brand-new** Longhorn volume (`accessMode:
  rwx`), then a static PV and a target-namespace PVC of the same name bound to
  it. The source PVC/PV are never modified and stay bound in the source
  namespace as the rollback copy.
- **Nothing is deleted until a separate, later step.** The source git folder
  is moved (`git mv`, not deleted) in one commit, and the safety `pg_dump` is
  kept. Both survive until the explicitly-gated reclaim procedure in section 7,
  which you only run after a healthy soak.

Recommended order for real moves (per `tasks/move-app-phase2-3-spec.md`):
dry-run both configs -> non-prod rehearsal -> `telemost-bot` (no volume,
lowest risk) -> soak -> `n8n`.

**Known gaps to check before relying on this for a real `n8n --execute` run**
(found while writing this runbook, not yet fixed in the tool):
- `scripts/dbmove-rehearsal.sh` is currently a stub (prints a placeholder
  line and exits) - the non-prod rehearsal that is supposed to gate the real
  n8n move has not actually been built/run yet.
- The `longhorn-backup` step resolves the source PV name but its real
  (`--execute`) `kubectl create -f -` call does not pipe any Snapshot/Backup
  manifest to stdin, so it does not currently trigger a new Longhorn backup.
  `volume-copy`'s restore step depends on `backupvolume.status.lastBackupName`
  already being set, so confirm a completed Longhorn backup exists for
  `n8n-data` and `n8n-worker-data` (recurring job or manual) before trusting
  `volume-copy` on a real run.

## 3. Procedure

Run from `tools/dbmove/`. For each app (`n8n` or `telemost-bot`):

1. Dry-run (this is the DEFAULT - no flag needed):
   ```
   go run . --config configs/n8n.yaml
   ```
   Read every `[dry-run]` line it prints. Nothing is mutated in dry-run.
2. Once the plan looks right, execute for real:
   ```
   go run . --config configs/n8n.yaml --execute
   ```
   (Equivalent: `./dbmove --config configs/n8n.yaml --execute` using the
   binary built in section 2.)
3. Push the argo-infra commit `folder-move` created - this is what makes the
   `tenant-apps` ApplicationSet regenerate the app under the target
   project/namespace. Nothing is live in the target until this push lands:
   ```
   git -C /Users/alex/IdeaProjects/argo-infra push origin console-migration
   ```

### Step order (from `tools/dbmove/plan.go` `BuildPlan`)

Steps run in this fixed order; step IDs are stable and are what `--only`/`--from` match against.

| # | Step ID | What it does | Applies to |
|---|---------|---------------|------------|
| 1 | `safety-dump` | Creates a Kanister `ActionSet` (blueprint `postgres-logical-db-blueprint`, profile `dada-db-backups`, target `StatefulSet databases/postgresql`) that `pg_dump`s the logical DB to `dumps/dbmove/<dbDatname>/db-move-<dbDatname>.dump`; polls up to 15 min for `status.state` to contain `complete` | both |
| 2 | `longhorn-backup` | Resolves each source PVC's bound PV name; intended to trigger a Longhorn snapshot+backup (see known gap above) | n8n only |
| 3 | `scale-down` | Scales each `scaleDeployments` entry to 0 in the source namespace | n8n only |
| 4 | `volume-copy:<pvc>` (one per volume, in config order) | Reads the source PVC's real size, finds its latest completed Longhorn backup, restores it into a fresh RWX volume named `<app>-<pvc>-moved`, a static Retain PV `<that>-pv`, and a target-namespace PVC named exactly `<pvc>` bound to it; waits up to 10 min for the volume to report `healthy` | n8n only (`volume-copy:n8n-data`, then `volume-copy:n8n-worker-data`) |
| 5 | `copy-secrets` | For each `oobSecrets` entry: `kubectl get secret -o yaml` from the source namespace, strips server-managed metadata (resourceVersion, uid, creationTimestamp, generation, ownerReferences, managedFields, status) and rewrites `metadata.namespace`, then `kubectl apply`s into the target namespace | both |
| 6 | `folder-move` | `git mv` the app folder from `projects/<srcProject>/environments/<srcEnv>/apps/<app>` to `projects/<targetProject>/environments/<targetEnv>/apps/<app>` inside the argo-infra checkout; rewrites `namespace:`/`dada.io/project:` literals in `resources.values.yaml` and, if the app has volumes, `ReadWriteOnce` -> `ReadWriteMany` in `chart/templates/deployment.yaml` and `worker.yaml`; commits as `chore(move): <app> <srcProject> -> <targetProject> (dbmove)` | both |
| 7 | `verify` | Probes `select 1` and a live row count against the redelivered target-ns credentials; for volumes, compares a `sha256` file manifest of the target PVC against the still-retained (and, since scale-down, unwritten) source PVC | both |
| 8 | `teardown` | Best-effort reattributes the console `resource_snapshots` row (`kind='App'`) to the target project/environment by exec-ing into `deploy/dada-cloud-console-backend` in `platform-prod` (always that namespace/deployment, regardless of which app you moved - that is where the console's own DB lives); prints the manual SQL instead if unreachable; always prints the retained-source reclaim checklist. Never deletes anything | both |

So the two concrete plans are:
- **telemost-bot:** `safety-dump, copy-secrets, folder-move, verify, teardown`
- **n8n:** `safety-dump, longhorn-backup, scale-down, volume-copy:n8n-data, volume-copy:n8n-worker-data, copy-secrets, folder-move, verify, teardown`

### `--from` / `--only`

- `--from <stepID>` resumes the plan starting at that step (skips everything before it) - use after fixing a mid-plan failure.
- `--only <stepID>` runs a single step and skips the rest - use to re-check one thing (e.g. `--only verify`).
- These two flags are **mutually exclusive**: passing both exits immediately with an error (exit code 2). You cannot "resume from X but only run Y" in one invocation.

## 4. Per-app facts

### n8n -> platform-prod

- Config: `tools/dbmove/configs/n8n.yaml`. `dbDatname: n8n`, `dbCredSecret: n8n-db-credentials`.
- Volumes (RWO -> RWX during the move): `n8n-data` (mounted by `n8n`, currently unmounted - main is 0/0) and `n8n-worker-data` (mounted by `n8n-worker`), 2Gi each, `longhorn-prod`.
- `scaleDeployments`: `n8n`, `n8n-runners`, `n8n-worker`. n8n main is `replicas: 0` in git (worker-only); scaling it is a no-op. The real, brief scale-to-0 window is `n8n-worker`, for a crash-consistent volume snapshot.
- Out-of-band secrets (hand-created, do NOT follow the namespace on their own - must be copied by `copy-secrets` before the workload starts): `n8n-runtime` (keys include `encryptionKey`, `basicAuthUser`, `basicAuthPassword`, `runnersAuthToken`, `smtp-password`) and `n8n-smtp`. **`encryptionKey` is data-critical**: n8n encrypts stored workflow credentials with it, so if the target ever ends up with a different key, the DB rows copy fine but become permanently undecryptable. `n8n-runtime` in the source namespace is the source of truth.
- Public domains: `n8n.dada-tuda.ru` and `n8n-64b3d0.dada-tuda.ru`. Expect a brief 404 on both while the TLS cert re-issues in the new namespace.

### telemost-bot -> internal-prod

- Config: `tools/dbmove/configs/telemost-bot.yaml`. `dbDatname: telemostbot`, `dbCredSecret: telemost-bot-db-credentials`.
- No volumes (`volumes: []`) - so `longhorn-backup`, `scale-down`, and `volume-copy` are not part of its plan at all (`BuildPlan` only adds them when `len(cfg.Volumes) > 0`); the `scaleDeployments: [telemost-bot-deploy]` entry in its config is currently inert for that reason.
- Out-of-band secrets: `telemost-bot-llm-keys` and `telemost-bot-keycloak`.
- No public domain.
- Near-zero downtime: DB-only re-point, both namespaces can reach the same shared DB during cutover.

## 5. Evidence checklist per verify gate

Capture all of these before moving on to teardown/soak:

- [ ] **Safety dump present + size in S3** - `kubectl --context 83.222.27.62:26443 -n databases get actionset -l dada.io/dbmove=<app> --sort-by=.metadata.creationTimestamp -o yaml` shows `status.state: complete`; note the size of `dumps/dbmove/<dbDatname>/db-move-<dbDatname>.dump` in the backup target.
- [ ] **`dbmove-probe` `select 1`** - the `verify` step's psql probe against the redelivered target-ns credentials must return exactly `1`.
- [ ] **A known row count in the target ns** - `verify` prints a live count via `select coalesce(sum(n_live_tup), 0) from pg_stat_user_tables` (an estimate from Postgres stats, not an exact `COUNT(*)`). Since the DB is a re-point and not a copy, this is a connectivity/auth smoke test, not an automatic before/after diff - sanity-check it against a number you know for the app (the tool does not store or compare a pre-move baseline for you).
- [ ] **Target PVC `Bound` + `sha256` file-manifest matches pre-move (n8n only)** - `verify` does this automatically by comparing the target PVC's manifest against the still-retained, unwritten source PVC; it fails the step on any mismatch.
- [ ] **Pods `Ready` in the target ns.**
- [ ] **`n8n.dada-tuda.ru` returns 200 (basic-auth) for n8n.**

## 6. Rollback (mid-flight, before teardown)

- **Abort before `folder-move`:** the source is still fully live. If `scale-down` already ran, scale the touched deployments back up (`kubectl --context 83.222.27.62:26443 -n example-project-prod scale deploy/<name> --replicas=<original>`). Anything `volume-copy`/`copy-secrets` created in the target namespace is an inert copy - leave it or delete it, it does not affect the source.
- **Abort after `folder-move`:** find the move commit (`chore(move): <app> example-project -> <target> (dbmove)`) in the argo-infra checkout and revert it, then push:
  ```
  git -C /Users/alex/IdeaProjects/argo-infra log --oneline -5
  git -C /Users/alex/IdeaProjects/argo-infra revert <that-commit-sha>
  git -C /Users/alex/IdeaProjects/argo-infra push origin console-migration
  ```
  (If revert conflicts, fall back to manually `git mv`-ing the folder back to its original path, reverting the literal edits, committing, and pushing.) The ApplicationSet re-derives the source Application from the restored path. Source data never left: PVs stayed `Retain`, the DB stayed `Orphan`, and the safety dump is still there - nothing about the rollback depends on data actually moving back.

## 7. Reclaim source (separate, explicitly gated - run only after a healthy soak)

This is the one genuinely destructive action in the whole move. Do not run it
until the owner has confirmed the target has soaked healthy. It is irreversible.

For n8n (2 volumes; telemost-bot has none, so its reclaim is dump expiry only):

```
# 1. Resolve the source PV names first (they are auto-generated, not fixed strings)
kubectl --context 83.222.27.62:26443 -n example-project-prod get pvc n8n-data n8n-worker-data \
  -o jsonpath='{range .items[*]}{.metadata.name}{"="}{.spec.volumeName}{"\n"}{end}'

# 2. Delete the source PVCs (namespaced; does NOT delete the PV, since reclaimPolicy is Retain)
kubectl --context 83.222.27.62:26443 -n example-project-prod delete pvc n8n-data n8n-worker-data

# 3. Delete the now-Released source PVs - IRREVERSIBLE, data is gone once Longhorn garbage-collects the volume
kubectl --context 83.222.27.62:26443 delete pv <pv-name-for-n8n-data> <pv-name-for-n8n-worker-data>
```

Then expire the safety dump(s) - `dumps/dbmove/n8n/db-move-n8n.dump` and/or
`dumps/dbmove/telemostbot/db-move-telemostbot.dump` in the `dada-db-backups`
backup target - per normal retention.

**Warning:** step 3 above and the dump expiry cannot be undone. Get explicit
owner confirmation of a healthy soak before running any part of this section.
