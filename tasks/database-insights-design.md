# Database Insights — что происходит в базе, глазами владельца

## Откуда взялось

Клиент (`odds-research`, проект `cd6481fa`) пришёл с запросом «поднимите
shared_buffers». Диагностика показала, что он прав по механике, но ни он, ни мы
не могли это увидеть: у платформы не было ни одного инструмента, отвечающего на
вопрос «какой запрос ест инстанс». Разбор занял два часа ручной форензики по
`pg_stat_user_tables`, `pg_statio_user_tables` и `pg_stat_user_indexes`.

Тот же набор данных, собранный регулярно, закрывает две разные потребности
одним конвейером:

- **тенанту** — «что творится в моей БД: размеры таблиц, медленные запросы,
  неиспользуемые индексы, откуда рост»;
- **платформе** — «кто из тенантов сейчас топит шардированный инстанс».

Это один сборщик и два потребителя. Строить надо сразу так.

## Что удалось выяснить про odds-research (форензика вручную)

Инстанс: shared `databases/postgresql-0`, 33 логические БД, том 26Gi.
`odds-research` — 15 GB, 68% занятого места. Второй по размеру объект на
инстансе — 284 MB.

Таблицы:

| таблица | размер | heap-чтений с диска | попаданий в кэш | hit ratio |
|---|---|---|---|---|
| `bookmaker_event_relationships` | 420 MB | 131 054 752 | 8 262 500 | 6% |
| `bookmaker_event_observations` | 3930 MB | 17 158 016 | 288 210 | 2% |
| `bookmaker_market_observations` | 4885 MB | 9 060 632 | 245 137 | 3% |
| `bookmaker_selection_observations` | 5422 MB | 509 329 | 271 522 | 35% |

131 миллион блоков по 8 kB — это ~1 ТБ физического чтения за 9 часов с одной
таблицы размером 420 MB. Таблица помещается в кэш целиком двадцать раз, но
`shared_buffers` был 128 MB на весь инстанс. Каждый сосед платил за это.

Паттерн записи — чистый append: `n_tup_upd = 0`, `n_tup_del = 0` по всем
крупным таблицам. Ничего никогда не удаляется, ретенции нет.

`last_autovacuum` и `last_autoanalyze` показывали NULL на всех крупных
таблицах, но это **не** доказательство того, что автовакуум не отрабатывал:
счётчики `pg_stat_user_tables` обнуляются при рестарте инстанса, а под
перезапускался за 9 часов до замера. Проверка через `reltuples` после ручного
`ANALYZE` дала 14.4M против 12.5M до него — статистика собиралась и была
близка к правде. Это отдельный урок для сборщика: любой вывод «за всё время»
из счётчиков, которые сбрасываются при рестарте, надо считать неверным по
умолчанию.

Индексы: `bookmaker_selection_observations_pkey` 562 MB / 0 сканов,
`uq_bookmaker_event_relationship_observation` 185 MB / 0 сканов,
`bookmaker_event_relationships_pkey` 56 MB / 0 сканов — около 800 MB индексов,
которые только пишутся.

Рост: всплеск 08-04 18:13 → 08-05 04:43 с 7.45 до 14.66 GB, ровно +0.30 GB за
30 минут. Последние 9 часов — +0.004…0.053 GB за 30 минут, то есть на порядок
медленнее. Версия клиента (старый конвейер писал снапшот линии целиком,
вчера выкачен режим «только изменения») этому соответствует.

### Что показал pg_stat_statements сразу после включения

Через четыре минуты работы расширения ответ, который до этого был недоступен
в принципе:

| БД | доля времени инстанса | вызовов |
|---|---|---|
| `odds-research` | **96.3%** | 148 221 |
| `postgres` | 1.9% | 739 |
| `cloud-console` | 1.3% | 2 829 |
| `keycloak` | 0.3% | 3 940 |

Внутри `odds-research` один запрос съел 44.7 секунды за **один** вызов, вернув
904 строки:

```sql
SELECT DISTINCT ON (bookmaker_event_observations.bookmaker_event_id) ...
FROM bookmaker_event_observations
JOIN bookmaker_events ON bookmaker_events.id = bookmaker_event_observations.bookmaker_event_id
WHERE bookmaker_event_observations.rule_set_id = $1::UUID
ORDER BY bookmaker_event_observations.bookmaker_event_id,
         bookmaker_event_observations.observed_at DESC,
         bookmaker_event_observations.observation_id DESC
```

На таблице всего два индекса, и оба бесполезны для этого запроса:
`(id)` и `(bookmaker_event_id, observation_id, rule_set_id)` — `rule_set_id`
третьей колонкой, ведущим фильтром работать не может. Значит seq scan по
3930 MB плюс сортировка, каждый раз.

Второй по чтению — запрос по `bookmaker_event_relationships`
`WHERE relationship_type = $1 AND child_event_id IN (...)`: единственный
подходящий индекс начинается с `parent_event_id`, поэтому опять seq scan, и
это ровно те 131M блоков с диска из таблицы выше.

Лечится двумя индексами:

```sql
CREATE INDEX CONCURRENTLY idx_beo_ruleset_event_observed
  ON bookmaker_event_observations (rule_set_id, bookmaker_event_id, observed_at DESC, observation_id DESC);

CREATE INDEX CONCURRENTLY idx_ber_child_type
  ON bookmaker_event_relationships (child_event_id, relationship_type);
```

Это данные владельца — индексы создаёт он, не мы.

Главный вывод здесь не про клиента, а про нас: диагностика заняла два часа
ручной работы, а после включения одного расширения — четыре минуты. Разница
между этими двумя числами и есть продукт.

## Что уже сделано

`argo-infra@851d2747`, `namespaces/databases/postgresql/values.yaml`:

- контейнер 3Gi request / 6Gi limit (было 228Mi / 1Gi);
- `shared_buffers` 1536MB, `work_mem` 16MB, `maintenance_work_mem` 512MB;
- `random_page_cost` 1.5 и `effective_io_concurrency` 200 — было 4 и 1,
  настройки под шпиндель, а под нами SSD-backed Longhorn;
- `max_wal_size` 1536MB — не больше, потому что на томе 8.4 GB свободно;
- **`shared_preload_libraries = 'pgaudit,pg_stat_statements'`**,
  `track_io_timing = on`, `log_min_duration_statement = 1000`.

Последний пункт — фундамент всего, что ниже. Без него продукта нет.

## Продукт

### Слой 1. Сборщик

Один воркер в console-backend, тикает раз в 60 секунд, ходит на каждый
шардированный инстанс под админской ролью (та же, что у provider-sql
ProviderConfig) и снимает пять срезов:

| источник | что даёт |
|---|---|
| `pg_stat_statements` | queryid, calls, total/mean exec time, rows, shared_blks_read/hit, temp_blks — с `dbid` |
| `pg_stat_user_tables` + `pg_total_relation_size` | размер heap/индексов, n_tup_ins/upd/del, n_dead_tup, last_autovacuum |
| `pg_stat_user_indexes` | idx_scan, размер — неиспользуемые индексы |
| `pg_stat_database` | blks_hit/read, numbackends, deadlocks, temp_bytes |
| `pg_stat_activity` | живые долгие запросы, idle in transaction |

`pg_stat_statements` глобален по инстансу и размечен `dbid` → маппинг на
логическую БД → на `ServiceDatabaseV2` → на app/project. Атрибуция «кто ест
инстанс» получается бесплатно, тем же запросом, что и тенантский вид.

Хранение: дифф-семплы в таблицах `db_stat_statements`, `db_stat_tables`,
`db_stat_indexes` в `cloud-console`. Счётчики в PG кумулятивные и сбрасываются
при рестарте — сборщик должен детектить сброс (`stats_reset`, падение
счётчика) и не рисовать отрицательные дельты. Ретенция 30 дней, посуточная
свёртка дальше.

Стоимость: 33 БД × 5 запросов раз в минуту. Ощутимо дешевле, чем один
`SELECT` клиента по 15 GB.

### Слой 2. API

```
GET /api/v1/projects/{p}/apps/{a}/database/insights
  → { sizeBytes, sizeLimitBytes, growth7d, cacheHitRatio, connections{used,limit}, tier }
GET /api/v1/projects/{p}/apps/{a}/database/tables?sort=size|growth|deadTuples
  → [{ schema, name, heapBytes, indexBytes, rowsEstimate, deadTuples, lastAutovacuum, growth7d }]
GET /api/v1/projects/{p}/apps/{a}/database/queries?window=1h|24h|7d&sort=totalTime|calls|ioRead
  → [{ queryId, sample, calls, meanMs, p95Ms, totalMs, rowsPerCall, sharedBlksRead, share }]
GET /api/v1/projects/{p}/apps/{a}/database/advisories
  → [{ code, severity, subject, detail, suggestedSql }]
GET /api/v1/projects/{p}/apps/{a}/database/activity
  → живой pg_stat_activity, только эта БД
```

Авторизация — по владению app, как у остальных app-эндпоинтов. Текст запроса
из `pg_stat_statements` уже нормализован (константы заменены на `$1`), но
`track_activity_query_size` мы подняли до 4096, а в `pg_stat_activity` сырые
константы **есть** — их надо резать до нормализованного вида перед отдачей,
иначе в консоль утекут значения из чужих... нет, из своих же данных клиента,
но всё равно PII-риск. Отдавать `query` из activity только владельцу app.

Бюджет: эндпоинты читают из `cloud-console`, не из тенантской БД, поэтому
укладываются в правило 300ms. Живой `activity` — единственный, который ходит
на инстанс, и он вне бюджета простых эндпоинтов.

### Слой 3. Advisories — то, ради чего это стоит делать

Таблица и график — это то, что даёт любой pgAdmin. Продукт начинается там, где
консоль сама говорит, что не так. Правила выводятся прямо из разбора выше:

| code | триггер | что показываем |
|---|---|---|
| `unused_index` | `idx_scan = 0` за 7 дней и размер > 50 MB | «индекс X занимает 562 MB и не использовался ни разу; `DROP INDEX`» |
| `stale_stats` | `last_autoanalyze` старше 7 дней **и** аптайм инстанса больше этого срока | «статистика по X не обновлялась N дней; `ANALYZE X`» |
| `append_only_no_retention` | `n_tup_del = 0`, рост > 1 GB/нед | «таблица только растёт, удалений нет; при текущем темпе квота через N дней» |
| `low_cache_hit` | hit ratio < 90% и blks_read > порога | «X читается с диска, а не из кэша: N GB физического чтения за сутки» |
| `slow_query` | mean > 1s или доля total_time > 20% | текст запроса + доля от общего времени БД |
| `quota_forecast` | линейная экстраполяция роста до `storageLimit` тира | «место кончится DD.MM» |
| `idle_in_transaction` | сессия > 5 минут | «соединение держит транзакцию N минут, блокирует вакуум» |

`quota_forecast` — тот самый мост к тирам из
[postgres-multitenancy-design.md](postgres-multitenancy-design.md): квота
перестаёт быть внезапной стеной и становится приборной панелью, которую видно
за две недели до удара.

### Слой 4. Консоль

Вкладка **Database** на странице приложения, четыре блока:

1. шапка — размер против квоты тира, рост за 7 дней, hit ratio, соединения;
2. **Advisories** — первым экраном, не последним. Если платформа знает, что не
   так, это должно быть видно раньше графиков;
3. **Карточки таблиц** — таблица как объект консоли, наравне с app и доменом:
   карточка с размером, спарклайном роста, числом строк и чипами алертов
   (append-only, мёртвый индекс, низкий hit ratio). Клик → страница таблицы:
   схема колонок, индексы и их использование, запросы именно по этой таблице,
   её алерты;
4. **Queries** — топ по суммарному времени, с переключателем окна и сырым
   нормализованным текстом.

Мокап и рыночная разведка: концепт-артефакт + db-insights-market-research.md.

Плюс блок «Live activity» с текущими запросами и кнопкой отмены своего
собственного запроса (`pg_cancel_backend` строго в пределах своей БД).

## Порядок работ

1. Сборщик + миграции таблиц. Без UI. Проверка: сутки данных по всем 33 БД,
   дельты не уходят в минус после рестарта инстанса.
2. Advisories-движок поверх собранного. Проверка: на `odds-research` он
   обязан сам, без подсказок, выдать `unused_index` × 3,
   `append_only_no_retention` и `low_cache_hit` — то, что я нашёл руками.
   Это и есть критерий приёмки, а не «эндпоинт отвечает 200».
3. API-эндпоинты.
4. Вкладка Database в консоли.
5. Платформенный вид: тот же сборщик → `/admin` «кто ест инстанс», топ-N БД по
   total_exec_time и по физическому чтению. Отсюда же берётся автоматическое
   назначение тира и алерт о шумном соседе.

Шаг 5 не отдельный проект. Он выпадает из шагов 1-2 почти бесплатно, и
именно он закрывает исходный вопрос — «не давать одному тенанту положить
постгрес» — не квотой вслепую, а с именем виновника.

## Миграции схемы: наблюдаем, не гейтим

Гейт на миграции невозможен: любое навайбкоженное приложение накатывает свой
alembic/hibernate/prisma при старте, мимо любого нашего ревью, и гейт будет
либо врать, либо конфликтовать с чужим механизмом. Поэтому:

- **наблюдение пассивное** — снапшот схемы после каждого изменения
  (event trigger или дифф при тике сборщика), advisory постфактум:
  «новая колонка X участвует в WHERE без индекса»;
- **изменения от агента — кодом через PR** для проектов с репо: механизм
  облачных агентов с PR уже есть, изменение схемы приезжает туда, где живут
  миграции владельца, и катится его же конвейером;
- **UI/MCP-миграции** — для новичков без репо и без настроенных миграций:
  консоль сама ведёт историю применённых изменений и умеет их откатывать.

## Что осознанно не делаем

- Не показываем тенанту чужие БД и чужие queryid, даже агрегатами. `dbid` —
  жёсткий фильтр на уровне SQL сборщика, не на уровне API.
- Не даём `EXPLAIN` из консоли на первом шаге: он выполняется на живом
  инстансе и сам по себе может быть дорогим. Позже — с таймаутом и только
  `EXPLAIN` без `ANALYZE`.
- Не даём менять параметры БД из консоли. Тир — единственная ручка. Иначе
  вернёмся ровно к тикету, с которого всё началось.
