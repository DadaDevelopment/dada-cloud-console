# Готовые проекты: одна строка, одно окружение, две невидимые реализации

**Статус:** дизайн. Продолжение PR «готовые проекты вместо стартеров»
(`backend/internal/solutions`), который закрыл только облачный трек и только
сборку из исходников.

**Владельческая рамка (2026-08-06):** граница между облаком и VPS у нас почти
стёрлась — одна абстракция, две невидимые для пользователя реализации, один UI.
Значит каталог готовых проектов обязан работать и на VM, и делать это не
вторым каталогом, а тем же.

## Что есть у Бегета и где у него шов

Проверено по их страницам: **59 приложений**, установка либо при создании
сервера (приложение выбирается там же, где ОС), либо через раздел
**Marketplace** в панели — поиск по названию, иконка, кнопка **«Установить»**,
затем **«выбрать домен»** и уведомление с адресом и данными для входа. Дальше
домен и бесплатный Let's Encrypt подключаются отдельно, в разделе «Сайты».

Модель у них честная и понятная: **приложение = образ, запечённый на VM**. Из
неё же следуют её границы, и это ровно те места, где мы можем быть не «дешевле
на рубль», а другого класса:

| | Бегет | Что мы можем |
|---|---|---|
| Единица | приложение на VM | Application в Environment; VM или облако — реализация |
| Откуда берётся | 59 приложений, упакованных вендором | те же готовые + **любой публичный репозиторий**, собранный у нас |
| Домен и TLS | отдельный шаг после установки | часть установки |
| БД | ставится тем же образом рядом | managed-БД как отдельный ресурс, подключается переменной |
| Куда ставится | на эту VM | облако / своя VM / новая VM — выбор в одном селекте |

Вывод для дизайна: копировать их каталог смысла нет. Смысл в том, что у нас
**одна установка умеет три вещи, которых у них нет**: собрать чужой исходник,
приложить домен с TLS и БД сразу, и положить результат туда, куда попросят.

## Модель

Три сущности, и ни одна не знает про «облако против VPS».

### 1. Запись каталога = спецификация, нейтральная к рантайму

```
Entry{
  slug, name, tagline, icon, categories, aliases[]   // «post…» находит postgres
  delivery: image | source                            // ЕДИНСТВЕННОЕ различие
     image:  ref + версия, порт, команда
     source: repo + branch + root_dir + framework, порт
  needs:   []Dependency{ postgres | redis | ... }     // → managed-ресурс
  wants:   Domain{ tls: true } | nil                  // → домен на установке
  state:   Volume{path, size} | nil
  params[], secrets[]                                 // env, шифруется
}
```

`delivery` — это то место, где живёт всё различие между «тык по картинке n8n» и
«собери мне вот этот репозиторий». Не два каталога, не два экрана, не два API:
одно поле. Всё остальное — порт, тома, зависимости, домен, переменные — общее,
потому что для запущенного приложения происхождение образа уже не важно.

### 2. Цель = Environment, а не рантайм

Пользователь выбирает **куда**: «Облако», «Моя VM `findata`», «Новая VM».
`environments.runtime ∈ {k8s, vm}` уже существует и уже несёт `app_server_id`.
Установщик не ветвится на «облако или VPS» — он вызывает рендерер окружения:

- `k8s` → App CR + Helm values (существует)
- `vm` → сервис в агрегатном `compose.yaml` окружения (существует)

Оба уже умеют образ, порт, тома, переменные. Это и есть «две невидимые
реализации»: они не появляются в дизайне установки, они появляются на один
уровень ниже, в рендерере.

### 3. Резолвер строки = одна ручка на три сценария

`POST /resolve {query}` → упорядоченный список кандидатов:

- совпадение по каталогу (имя, алиасы, категория) → карточка с иконкой
- распознанная ссылка на репозиторий → карточка репозитория
- иначе — поиск по GitHub (наш токен, кеш) → карточки репозиториев

Одно поле ввода. Новичок печатает `n8n` и видит иконку. Тот, кому нужен
Postgres, печатает `post` и видит Postgres первым, потому что каталог всегда
ранжируется выше поиска. Про вставляет ссылку на gitbucket и видит репозиторий.
Никаких режимов, вкладок и «сначала выберите тип».

## Три сценария через эту модель

**Новичок: тык по картинке n8n → n8n с доменом и БД.**
`resolve("n8n")` → каталожная запись `delivery: image`, `needs: [postgres]`,
`wants: domain{tls}`. Мастер показывает один экран: куда ставим (облако / новая
VM), имя, и что будет создано — приложение, база, домен. Установка создаёт
managed-БД, кладёт её DSN в переменные приложения (механизм seedEnvVar уже
существует и уже так работает для баз), выпускает домен и отдаёт ссылку с
логином. Ровно бегетовский сценарий, но БД и домен не «потом в разделе Сайты», а
внутри той же кнопки.

**OSS-юзер: `post…` → Postgres в один тык; или ссылка на репозиторий.**
Тот же резолвер, тот же мастер. Managed-БД — это не приложение из каталога, а
ресурс платформы, но в выдаче он выглядит такой же карточкой с иконкой: для
человека «поднять postgres» — одно действие, и различие «ресурс против
приложения» его не касается.

**Про: URL произвольного репозитория → в облако или в свою VM внутри контура.**
`delivery: source`, детект фреймворка (уже есть, включая `EXPOSE` из
Dockerfile и монорепы), сборка в нашем пайплайне, деплой в выбранное окружение.
«Внутри контура» — это ровно выбор его VM в том же селекте, без отдельного
продукта.

## Что мешает сделать это by design прямо сейчас

Честный список швов, проверенный по коду. Каждый — не «доработка UI», а условие
того, чтобы одна абстракция не разъехалась на две.

1. **Домены и TLS на VM-треке отсутствуют.** `domain_hostnames` и
   `AttachCustomHostname` рендерят k8s Ingress, который VM-рендерер не читает;
   автоматики сертификатов на VM нет вовсе. Пока это так, «с доменом» работает
   только в облаке, и обещание «две невидимые реализации» ломается на первом же
   сценарии. Самый крупный из швов.
2. **У приложения, созданного сборкой, нет тома.** Спека берётся из `git_repos`
   (порт/реплики/профиль), тома там нет — поэтому текущий каталог состоит
   только из проектов без состояния. Пока не появится, `delivery: source` и
   `state: Volume` несовместимы.
3. **Именованные тома на VM пинятся `external: true`, но никто их не создаёт.**
   Первый деплой приложения с новым томом на чистой VM упрётся в отсутствующий
   том. Лечится созданием тома через Docker API Portainer перед деплоем стека
   (идемпотентно: существующий том не трогаем — инвариант сохранности данных).
4. **Managed-БД есть на обоих треках** (k8s — ServiceDatabase, VM — сервис
   postgres/redis с томом), но `needs` как декларации не существует: сегодня
   базу создаёт человек отдельным действием. Без неё сценарий новичка остаётся
   двумя кнопками вместо одной.
5. **Поиска по GitHub нет.** Нужен прокси GH Search API с нашим токеном и
   кешем: анонимный лимит — 60 запросов в час на весь исходящий IP кластера,
   одна интерактивная строка съест его за минуту.

## Порядок

Не «сначала UI, потом заткнём дыры» — швы выше и есть работа.

1. **Резолвер + поиск по GitHub** (закрывает 5). Одна строка, одна выдача, без
   новых деплой-путей — сразу даёт сценарий 2 и 3 в облаке.
2. **`delivery: image` в каталоге + рендер в оба рантайма** (используем то, что
   уже есть в обоих рендерерах). Даёт «тык по картинке» в облаке и на VM.
3. **Создание томов на VM** (3) — разблокирует stateful-записи на VM-треке.
4. **`needs` → managed-БД + переменные** (4). Сценарий новичка становится одной
   кнопкой.
5. **Домены и TLS на VM** (1) — самый большой кусок, после него «две невидимые
   реализации» перестают быть обещанием.
6. **Том в build-спеке** (2) — снимает ограничение «только проекты без
   состояния» с сборки из исходников.

Бенчмарк автоподнимателя (`tasks/autodeploy-benchmark-50-oss.md`) идёт
параллельно: он определяет, насколько широким может быть `delivery: source`,
и его порог — условие расширения каталога за пределы проектов с корневым
Dockerfile.
