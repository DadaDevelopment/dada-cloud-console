# Postgres multi-tenancy: кластер + LB + шарды

Дизайн v2. Триггер — запрос клиента `artemmendeleev@gmail.com` поднять
`shared_buffers` до 2-4GB на своей БД. Разбор показал, что тюнить нечего:
у клиента нет своего постгреса, а общий инстанс не выдержит и текущей
нагрузки. v1 предлагал «пулы» (N StatefulSet из одного чарта) — отвергнуто
владельцем: это не масштабируется в кластер и не даёт единой точки входа.

## Целевая архитектура

```
apps ──► pg-router (LB: пулер-роутер, 2+ реплик, единый DSN навсегда)
              │  роутинг по dbname → шард (реестр в control plane)
     ┌────────┼─────────────┐
  shard-0   shard-1   ...  shard-N     (шард = primary + replica, свои ресурсы)
  ПЛАТФОРМА  клиенты        клиенты
```

Три компонента:

1. **Шарды** — независимые HA-инстансы Postgres. Каждая логическая БД целиком
   живёт на одном шарде. `shard-0` — только платформенное (`cloud-console`,
   `keycloak`, внутренние сервисы), клиентский трафик туда не роутится.
2. **pg-router (LB)** — фарм пулеров-роутеров перед всеми шардами. Приложение
   всегда коннектится на один и тот же хост; роутер по имени базы отправляет
   коннект на нужный шард и пулит нативные соединения.
3. **Реестр** tenant→shard — таблица в control plane, отражается в
   `ServiceDatabaseV2.spec.shard`, композиция выбирает `providerConfigRef`
   шарда. Плейсмент только автоматический.

## Как это делают снаружи (исследование 2026-08-06)

- **SPQR (Яндекс Cloud)** — роутер+координатор+etcd, шардирует ОДНУ схему по
  ключу шардирования: роутер парсит первый запрос транзакции, ребаланс
  ε-split диапазонов ключей, мультишард best-effort, 2pc без глобального
  snapshot isolation. Подходит для «одна таблица orders на терабайты».
  **Не наш случай**: у нас tenant = целая логическая БД, ключа шардирования
  нет, и его ограничения (парсинг SQL, распределённые транзакции) нам не
  нужны — БД и так атомарно лежит на одном шарде.
- **Supavisor (Supabase)** — наш случай один в один: multi-tenant
  пулер-кластер, реестр тенантов в отдельном Postgres, клиент коннектится в
  любую ноду, пул тенанта живёт на ноде-владельце, миллионы клиентских
  коннектов → пул нативных. Так сервятся сотни тысяч тенантов.
- **Yandex Managed PG** — каждый кластер за Odyssey (их пулер: 1M+ RPS на
  сотнях хостов, multithreaded, session/transaction pooling, авто-Cancel и
  Rollback брошенных транзакций при обрыве клиента).
- **Яндекс Такси (процессинг)** — virt-шарды: `hash(key) % N_virt` → статический
  маппинг в конфиге, без центрального координатора; решардинг фазами
  read-only → переключение записи → фоновая переливка → валидация.

Вывод: для DB-per-tenant индустрия строит **router + registry + шарды целыми
БД**, а не key-based шардирование. Key-based (SPQR/Citus) — если когда-нибудь
одна клиентская БД перерастёт шард; тогда она получает выделенный шард, и
только внутри него встаёт SPQR. Не сейчас.

## Компоненты подробно

### Шарды

- Шард = Postgres primary + streaming replica, anti-affinity по нодам,
  ресурсы от 4Gi RAM (не сегодняшний 1Gi), свой том, свой superuser-секрет,
  свой `ProviderConfig` (`postgresql-shard-N`).
- `shared_buffers` на шарде ставится под его RAM (25%), `pg_stat_statements`
  и `log_min_duration_statement = 1s` включены с рождения.
- Оператор HA (CloudNativePG либо продолжаем bitnami+ручной failover) —
  решить в шаге 1; CNPG даёт failover, backup-интеграцию и `-rw`/`-ro`
  сервисы из коробки, bitnami — то, что уже умеем.
- Существующий `databases/postgresql-0` становится `shard-1` (клиенты
  остаются на месте, ноль переездов в момент включения роутера).

### pg-router (LB)

- Кандидаты: **Odyssey** (Яндекс, multithreaded, cloud-scale) или
  **PgBouncer-фарм** (проще, per-db маппинг `dbname → host` в конфиге,
  масштабируется репликами за Service). Оба умеют роутить по имени базы на
  разные хосты. Выбор в шаге 2 по результату стенда; дефолт — PgBouncer как
  наименее рискованный, Odyssey — если упрёмся в CPU одного треда.
- Deployment ≥2 реплик за Service `pg-router.databases.svc` — этот хост
  зашивается во все connection-секреты вместо адреса инстанса. **DSN клиента
  больше никогда не меняется**, что бы мы ни делали с шардами.
- Конфиг (маппинг dbname→shard + auth) рендерится gitops-агентом из реестра
  тем же механизмом, что values приложений; reload онлайн, без разрыва.
- Auth: креды генерит наша композиция → SCRAM-хэши кладутся в auth-файл
  роутера из тех же секретов. Мы владеем всеми кредами — passthrough не нужен.
- Платформенное (`cloud-console`, `keycloak`) ходит на `shard-0` — либо через
  тот же роутер (отдельный listener/pool class), либо напрямую в
  `shard-0-rw`: решить в шаге 5; напрямую = SSO не зависит от роутера,
  через роутер = единая труба и единые метрики. Дефолт — напрямую:
  зависимость «вход в консоль требует живого роутера» опаснее, чем два пути.

### Реестр и плейсмент

- Таблица `db_shards` (shard, dsn-secret, capacity, state) +
  `spec.shard` на XR (аналогично уже сделанному `spec.tier`).
- Плейсмент при создании: платформенное → `shard-0`; клиентское → шард с
  наименьшей суммой `pg_database_size_bytes` среди открытых. Руками — никогда.
- Рост = добавить строку шарда. Реестр мал (десятки строк), etcd/координатор
  как в SPQR не нужен — хватает Postgres control plane, как у Supavisor.

### Переезд БД между шардами

Порядок как у Такси, но на уровне целой БД:
1. logical replication базы на целевой шард (или dump/restore для мелких);
2. quota-воркер ставит `read-only` (механизм уже есть — `spec.enforcement`);
3. догон реплики, валидация счётчиков;
4. флип строки реестра → rerender конфига роутера → reload;
5. снятие read-only, старая копия удаляется после срока хранения.
Клиент видит паузу записи в минуты, DSN не меняется.

## Тиры и квоты (сделано, ортогонально шардам)

Значения тиров в values чарта `crossplane-platform-api`, применяются через
`Role.connectionLimit` + `configurationParameters` — ноль ручных ALTER.

| тир | коннекты | размер | statement_timeout | idle_in_tx | temp_file_limit | work_mem |
|---|---|---|---|---|---|---|
| free | 15 | 1 GB | 15s | 30s | 512MB | default |
| starter | 40 | 5 GB | 30s | 60s | 2GB | 8MB |
| business | 100 | 25 GB | 120s | 300s | 8GB | 16MB |
| dedicated shard | по договору | по договору | настраиваемо | настраиваемо | настраиваемо | настраиваемо |

Размер — жёсткая квота: воркер `db_quota_state`, ступени warn 0.8 /
read-only 1.0 / frozen 1.25 / снятие 0.9, принуждение через
`spec.enforcement` → операция `SetDatabaseEnforcement`. CPU/IO квотируем
косвенно (timeout'ы + temp_file_limit), шумного соседа детектим по доле
`pg_stat_database_active_time_seconds_total` шарда.

## Наблюдаемость

- Дэшборд `Postgres shards`: на шард — коннекты/`max_connections`, том,
  cache hit ratio, deadlocks, `temp_bytes`, топ-5 баз по размеру и
  `active_time`; на роутер — клиентские vs серверные коннекты, время
  ожидания пула, ошибки роутинга.
- Карточка БД в консоли: размер/квота, коннекты/квота, шард, состояние
  (ok / warn / read-only), кнопка апгрейда тира.
- PrometheusRule (в dada-cloud, с `keep_firing_for`): коннекты шарда > 80%,
  том шарда > 80%, cache hit < 0.9 5м, база в read-only, лаг реплики,
  насыщение пула роутера.

      механика для этого уже лежит. Сделано: `routerAdmin.Cutover`
      (`1549f3fa`) — PAUSE на каждой реплике роутера, RELOAD с опросом, пока
      каждая не отчитается новым хостом, RESUME на любом пути выхода. Адреса
      реплик берутся из headless Service `pg-router-admin` (argo-infra
      `f7487b6e`): PAUSE через балансируемый Service попал бы в один под, а
      второй продолжал бы лить записи в покидаемый шард. Там же
      `routeSync.intervalSeconds` 60 → 5 и проверка файла reloader'ом 10 → 2
      секунды: это ровно то время, что арендатор стоит в очереди.
      Механика переезда дописана (`7e69f8b6`): `db_moves` + фазовая машина
      pending → preparing → schema → syncing → cutover → done. Схему копирует
      Job в ns `databases` (`aa6df02a` — RBAC; в образе консоли нет ни
      pg_dump, ни psql), данные догоняет логическая репликация `FOR ALL
      TABLES`, роль владельца переносится вместе со своим SCRAM-верификатором
      (роли кластерные), позиции последовательностей копируются внутри
      удержания — репликация их не переносит вообще. Маршрутизация слушает
      переезд: дошедший до cutover решает, где его база, пока снапшот CR не
      догонит. `DB_ROUTER_ADMIN_*` выставлены (argo-infra `46069fc4`).
      Осталось: (1) `DB_SHARD_ADMIN_DSNS` — он же включает сборщик инсайтов
      с соединением на каждую базу раз в 5 минут на том самом инстансе
      1 GiB, поэтому выставляется в момент реального переезда, не раньше;
      (2) прогон против пары живых инстансов — против кластера ничего из
      этого ещё не гонялось; (3) ручка/CLI — сейчас переезд заводится
      вставкой строки в `db_moves`; (4) привести `spec.shard` в CR в
      соответствие после переезда, иначе оверрайд держится вечно.

      07-08, боевое вооружение и первый прогон. Механика была мертва по трём
      независимым причинам, все три сняты:
      (a) `DB_SHARD_ADMIN_DSNS` лежал в ConfigMap, где его молча затирал
      Secret: `envFrom` применяет `configMapRef` раньше `secretRef`, а ключ,
      заданный в обоих, выигрывает из секрета. Значение переехало в
      `dada-cloud-console-backend`, в values.yaml оставлен комментарий, почему
      его там нет. Суперюзер нужен на ОБОИХ концах: копия SCRAM-верификатора
      роли, создание базы, publication/subscription, позиции
      последовательностей.
      (b) `wal_level = replica` на обоих шардах — логическая репликация была
      невозможна в принципе, а `max_wal_senders` не подсказал бы: отсутствие
      walsender'а выглядит как нулевой лаг. В `postgresql-extended-
      configuration` дописаны `wal_level = logical`,
      `max_replication_slots = 20`, `max_wal_senders = 20`; рестарт
      `postgresql-0` занял 25 секунд, 33 базы на месте.
      (c) Два бага воркера, оба нашлись на первом же прогоне
      (`dada-move-probe`, shard-1 → shard-0) и починены в `591a4b2d` вместе с
      пятью тестами на fake clientset: скрипт копирования схемы запускался
      через `/bin/sh`, а в `bitnamilegacy/postgresql:17.6.0-debian-12-r4` это
      dash — `set -o pipefail` там незаконен; и воркер объявлял переезд
      провалившимся по `Job.Status.Failed > 0`, то есть по ПЕРВОМУ упавшему
      поду, пока Job ещё ретраил. Правда о сдаче Job — условие `JobFailed`.

      Отдельно закрыт гейт для JDBC/pgx: при transaction pooling

      ходят и Keycloak, и консоль — каждый платформенный клиент падал бы на
      втором запросе, как только его DSN указал бы на роутер. В чарт добавлен

      подтверждают значение в `SHOW CONFIG`.

      Рычаг шага 4 включён живьём (argo-infra `4b5b0f8e`):

      Ловушка порядка, найденная тем же замером: значение из `secretKeyRef`

      07-08, боевой переезд. Прогнаны насквозь `dada-move-probe`, `n8n` и
      первая волна из шести простаивающих баз (`fanbot`, `mlflow-v2`,
      `telemostbot`, `recog`, `test-db-1`, `jira`) — все `done`, таблицы на
      обоих шардах совпали. Четыре вещи, которых в дизайне не было:
      (a) `track_extra_parameters` в роутере (argo-infra `442d0d31`).
      `ignore_startup_parameters` МОЛЧА выбрасывает параметр: клиент просит
      `statement_timeout` и работает без защиты, которую считает включённой.
      n8n нашёл это грубее — его драйвер шлёт `statement_timeout` на старте,
      pgbouncer отвечал «unsupported startup parameter», и каждый воркер
      уходил в CrashLoop, как только его DSN указал на роутер. Настройка
      `changeable = no`, то есть нужен РЕСТАРТ пода, и она ЗАМЕЩАЕТ дефолт —
      `IntervalStyle` приходится перечислять заново.
      (b) Владение объектами. `pg_dump --no-owner | psql` под админом оставляет
      всё принадлежащим админу, и приложение приезжает на копию, где его роль
      получает `permission denied for schema`. Добавлен `handOverObjects`
      (`0d743871`) — один DO-блок перед репликацией. Три грабли внутри:
      последовательность, привязанная к колонке, отдельно не переназначается
      (`pg_depend` deptype `a`/`i`), члены расширений (deptype `e`) на обоих
      шардах принадлежат админу и трогать их нельзя, а схема `public` в PG15+
      принадлежит `pg_database_owner`, что УЖЕ означает арендатора — первый
      живой прогон это сломал и был откачен.
      (c) `CREATE SUBSCRIPTION` возвращается, как только слот создан, а воркер
      подписки подключается мгновением позже. Ноль walsender'ов сразу после —
      это старт, а не мёртвый поток: два переезда (`recog`, `test-db-1`) были
      объявлены провалившимися, пока реально текли. Введены
      `errNoReplicationStream` и пятиминутная отсрочка (`ecd743db`).
      (d) Пункт (4) «привести `spec.shard` в CR» руками не закрывается:
      `resources.values.yaml` клиентских проектов ГЕНЕРИРУЕТСЯ агентом из базы
      консоли, правка в git затирается следующим рендером. Поэтому появилась
      операция `SetDatabaseShard` (`327112da`): дошедший до `done` переезд сам
      её заводит, агент патчит `spec.shard` в манифесте, который уже лежит в
      git — по образцу `SetDatabaseEnforcement`. Оверрайд `db_moves` остаётся
      примитивом cutover'а, а не хранилищем размещения.
      Не едут в общем потоке: базы, чей владелец — `postgres` (`codexlb`,
      `console-test`). Перенос роли скопировал бы верификатор суперпользователя
      с shard-1 на shard-0, то есть сменил бы админский пароль целевого шарда.
