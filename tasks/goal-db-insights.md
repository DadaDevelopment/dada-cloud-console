# GOAL — Database Insights

Одна цель на прогон. Всё, что не сверяется с ней, из работы выпадает.

## Формулировка

Владелец приложения открывает вкладку Database и без единого запроса к нам
видит, что происходит в его базе: размер против квоты, карточки таблиц,
топ запросов по времени и — первым экраном — advisories, которые платформа
вывела сама. Тот же сборщик даёт платформе имя шумного соседа.

## Критерий приёмки (не «эндпоинт отвечает 200»)

Движок advisories обязан **сам, без подсказок**, на живых данных
`odds-research` выдать то, что было найдено руками за два часа форензики:

- `unused_index` × 3 (562 MB / 185 MB / 56 MB, ноль сканов);
- `append_only_no_retention` (`n_tup_del = 0`, рост > 1 GB/нед);
- `low_cache_hit` (`bookmaker_event_relationships`, hit ratio 6%);
- `slow_query` на `DISTINCT ON ... rule_set_id` (доля времени БД > 20%).

Меньше — цель не достигнута, сколько бы кода ни было написано.

## Границы (HARD)

- Тенантские базы — **только чтение**. Никакого DDL, никаких индексов от нас:
  SQL отдаём текстом, выполняет владелец.
- Тестовые прогоны — только в `agent-sandbox`. Проекты не создавать.
- Дельты кумулятивных счётчиков не рисуем без детекта сброса (`stats_reset`,
  падение счётчика). Урок odds-research: NULL в `last_autovacuum` после
  рестарта не значит ничего.
- Гейта на миграции нет. Схему наблюдаем пассивно.
- Доставка — в `origin/main` через worktree + cherry-pick (рабочее дерево
  делит параллельная сессия), билд зелёный.

## Порядок

1. Сборщик + миграции таблиц статистики. Проверка: сутки данных по 33 БД,
   дельты не уходят в минус после рестарта инстанса.
2. Advisories-движок. Проверка — критерий приёмки выше.
3. API-эндпоинты.
4. Вкладка Database в консоли (шапка, advisories, карточки таблиц, queries).
5. Платформенный вид `/admin` — кто ест инстанс.
