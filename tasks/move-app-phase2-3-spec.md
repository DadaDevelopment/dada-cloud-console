# Stateful MoveApp — Phase 2/3 spec + migration runbook (n8n, telemost-bot)

Read `docs/adr/ADR-014-move-app-across-projects.md` and `tasks/move-app-phase1-spec.md`
first. This spec supersedes ADR-014's Phase 2/3 sketch with the ground truth verified
on prod (beget-prod + mgmt Argo) on 2026-07-23, and defines both deliverables the
owner approved:

- **Part 1 (now):** a gated, idempotent migration runbook + `dbmove` helper that moves
  `n8n` (example-project -> platform) and `telemost-bot` (example-project -> internal)
  without losing data.
- **Part 2 (after Part 1 proves out):** productize the proven mechanics into
  gitops-agent `doMoveApp` (MoveApp Phase 2/3) for future dada-managed stateful Apps.

Owner decisions (2026-07-23): both deliverables; DB = re-point (no dump/restore, no
rename); volumes = copy into fresh RWX (convert n8n's RWO -> RWX during the move,
source retained); execute autonomously once tested, with evidence at each verify gate.

## Ground truth (verified, not assumed)

1. **The DB is a logical database in ONE shared Postgres.** Every ServiceDatabaseV2 is
   a Crossplane `Database` + `Role svc-<name>` inside shared `postgresql-0` (ns
   `databases`, reachable at `postgresql.databases.svc.cluster.local`). The `Database`
   MR is `deletionPolicy: Orphan`, `providerConfigRef: postgresql-prod`, and its
   datname/role carry no namespace. The ServiceDatabaseV2 XR is cluster-scoped;
   `spec.namespace` only selects where the `<appRef>-db-credentials` connection secret
   is delivered.
   => **Re-homing the DB = change `spec.namespace`.** No data moves; `Orphan` means the
   logical DB cannot be dropped by the CR change. Both source and target namespaces reach
   the same DB with the same creds during cutover (no split-brain).

2. **n8n and telemost-bot are NOT dada-managed Apps.** No platform `App` CR exists
   (`kubectl get apps.platform.dada-tuda.ru` is empty for them). They are Argo
   Applications `n8n-prod` / `telemost-bot-prod` **generated by the `tenant-apps`
   ApplicationSet** (ownerReference controller=true) from a directory generator over
   `clusters/beget-prod/projects/*/environments/*/apps/*/` in
   `github.com/DadaDevelopment/argo-infra` (branch `console-migration`). They reuse the
   dada git-tree layout (`values.yaml` + `resources.values.yaml`) but n8n ships a bespoke
   `chart/` (in-tree) and telemost uses shared `helm/python` (dada-argo). The
   ServiceDatabaseV2 CR lives in each app's `resources.values.yaml` (rendered by
   `helm/app-resources`).
   => The Argo `MoveApp` op cannot move them (it reads an App snapshot that does not
   exist). The move is a **git-folder relocation in argo-infra** that the ApplicationSet
   turns into a new Application in the target namespace.

3. **Only namespace-bound data = n8n's volumes.** `n8n-data` + `n8n-worker-data`, 2Gi
   each, **RWO**, `longhorn-prod`, **reclaimPolicy=Retain**. `n8n-data` is currently
   unmounted (n8n main is 0/0); only `n8n-worker-data` is attached (to the running
   `n8n-worker`). telemost-bot has no volume. Longhorn backup target is configured
   (`s3://25f4da9f5cfe-dada-tuda-s3@ru1/`), default-replica-count=2.

4. **Backup/restore machinery** (backend, imperative Kanister ActionSet path,
   `backend/internal/api/db_backups.go`): `pg_dump -Fc --no-owner -d $DB` | kando push;
   restore is in-place into the SAME logical DB only. dumpPath =
   `dumps/<projectID>/<database>/<id>.dump`; blueprint `postgres-logical-db-blueprint`,
   profile `dada-db-backups`, target StatefulSet `databases/postgresql`. The imperative
   path ignores the CR's `spec.backup.enabled`, so a manual dump works for telemost-bot
   even though its `backup=false`.

## Namespaces / contexts

- Source: `example-project-prod`. Targets: `platform-prod` (n8n), `internal-prod`
  (telemost-bot). Namespace = `<project>-<env>`, derived from the git-tree path by the
  ApplicationSet.
- beget-prod kube context: `83.222.27.62:26443`. Mgmt Argo context:
  `e7b608-client-super-admin@e7b608-client`, ns `argocd-master`.
- `internal-prod` egress baseline already allows 5432 -> ns `databases`; confirm the same
  for `platform-prod` before cutover.

## Part 1 — migration runbook + `dbmove` helper

Deliverables:
- `docs/runbooks/stateful-app-move.md` — the operator runbook (human gates, evidence
  checklist, rollback).
- `dbmove` helper: a Go tool under `tools/dbmove/` that builds an explicit step plan and
  runs it, with a mandatory `--dry-run` that prints every mutation and executes nothing.
  Go (not bash) so the plan builder is unit-testable in isolation; it shells out to
  `kubectl` / the backend backup API / Longhorn CRs for the actual mutations. The runbook
  doc drives it.

The helper is a thin, auditable wrapper over `kubectl` / the backend backup API /
Longhorn CRs. It never hard-deletes: DB is `Orphan`, PVs are `Retain`, source git folder
is kept until the final teardown step. Every step is idempotent (checks current state
first) and re-runnable.

### Building blocks

**B1. Safety net (always first; nothing depends on it unless we abort).**
- Trigger a fresh `pg_dump -Fc` of the logical DB via the backend backup endpoint (or a
  direct Kanister ActionSet); wait for `Ready`; record dumpPath + size_bytes. Verify the
  object exists in S3.
- For n8n only: take a Longhorn snapshot of `n8n-data` and `n8n-worker-data` and confirm
  a completed backup to the Longhorn backup target.

**B2. Volume copy into fresh RWX (n8n only; source PVCs stay pristine).**
- Scale n8n workloads to 0 in the source ns (main + runners already 0/0; scale
  `n8n-worker` to 0) so the snapshot is consistent. Record replica counts to restore on
  rollback.
- For each source volume: create a Longhorn snapshot, back it up, then **restore into a
  new Longhorn volume with `accessMode=RWX`**. Materialize a target-ns PVC (`platform-prod`)
  named exactly as the chart expects (`n8n-data`, `n8n-worker-data`) bound to the restored
  RWX volume.
- Verify the target PVC is `Bound` and the data matches (file list + `sha256` manifest vs
  a pre-copy manifest taken from a read-only mount of the source snapshot).
- Source volumes are never surgically modified; they remain bound in the source ns as the
  rollback copy until final teardown.
- Impl check: inspect n8n's `chart/` PVC templating to confirm it adopts a pre-existing
  PVC by name (not `generateName` / not an inline volumeClaimTemplate that forces its own
  storageClass/accessMode). If the chart hard-codes RWO, add a values override to point at
  existing RWX PVCs.

**B3. DB re-point (automatic via Release.Namespace).**
- The chart renders the ServiceDatabaseV2 with `spec.namespace: {{ .Release.Namespace }}`
  (n8n `chart/templates/servicedatabase.yaml:12`; telemost via `helm/python` from
  `common.serviceDatabase`). The `tenant-apps` ApplicationSet derives the destination
  namespace from the folder path, so the folder move (B4) alone re-points
  `spec.namespace` to the target and Crossplane redelivers `<appRef>-db-credentials`
  there. `Orphan` keeps the logical DB intact. No manual `spec.namespace` edit needed.
- Verify from a target-ns probe pod: read the new secret, `psql 'select 1'`, and a
  row-count sanity check on a known table vs a pre-move count.

**B3b. Copy out-of-band Secrets to the target namespace (CRITICAL — data-loss vector).**
Some Secrets the apps consume are hand-created, NOT Crossplane-delivered, and do NOT
follow the namespace move. They must be recreated in the target ns before the workload
starts, or the app boots broken:
- **n8n:** `n8n-runtime` (keys: `encryptionKey`, `basicAuthUser`, `basicAuthPassword`,
  `runnersAuthToken`, `smtp-password`) and `n8n-smtp`. `encryptionKey` is data-critical:
  n8n encrypts stored workflow credentials with it; a fresh key makes the DB's credential
  rows undecryptable (effective data loss even though the DB copied fine). `n8n-runtime`
  is the source of truth for the key.
- **telemost-bot:** `telemost-bot-llm-keys` (Opaque) and `telemost-bot-keycloak` (verify
  whether it is Crossplane-delivered by a keycloak identity CR — if so it follows; if
  hand-created, copy it).
- Copy verbatim (same keys/values) into the target ns; verify key set matches before B4.
- Not applicable to the general dada MoveApp (Part 2): dada apps keep runtime config in
  `env_vars` which the move already copies; this step is specific to these raw apps'
  out-of-band secrets.

**B4. Workload move (atomic git-folder relocation in argo-infra).**
- In one commit on `console-migration`: move
  `clusters/beget-prod/projects/example-project/environments/prod/apps/<app>/` ->
  `clusters/beget-prod/projects/<target>/environments/prod/apps/<app>/`. Single commit so
  the `tenant-apps` ApplicationSet (git-files generator over `.../apps/*/app.yaml`) sees
  the app at exactly one path and the XR `spec.namespace` is an update-in-place, not
  delete+create.
- Edit namespace-bearing literals that do NOT auto-derive from the path:
  - **n8n `resources.values.yaml`:** the Ingress entry's `namespace: example-project-prod`
    -> `platform-prod`, and `dada.io/project: example-project` -> `platform` on the
    Ingress + both PublicApi entries. (The DB CR and Deployments/PVCs use
    `.Release.Namespace`, which follows the path — no edit.)
  - **n8n chart PVC access mode:** change `accessModes: [ReadWriteOnce]` ->
    `[ReadWriteMany]` in `chart/templates/deployment.yaml` and `worker.yaml` so Argo's
    desired PVC spec matches the pre-created RWX PVCs from B2 (a PVC spec is immutable;
    mismatch = sync error). n8n `chart/values.yaml` `common.persistence.storageClassName`
    stays `longhorn-prod` (RWX-capable).
  - **telemost-bot:** no `resources.values.yaml`, no volume, no explicit namespace
    literals -> pure folder relocation.
- The ApplicationSet regenerates the Application in the target project; destination
  namespace derives from the new path (`<target>-prod`). Argo brings the workload up
  adopting the pre-created RWX PVCs (n8n) and the redelivered creds. n8n `replicas: 0`
  (main) stays as-is in git — only `n8n-worker` runs; the main PVC (`n8n-data`) still
  moves so re-enabling main later finds its data.

**B5. Verify gate (evidence required before any teardown).**
- Target pods `Ready`; DB `select 1` + row-count matches pre-move; volume `sha256` manifest
  matches pre-move (n8n); public domain returns 200. Capture all as evidence.

**B6. Teardown (only after B5; still non-destructive).**
- The old folder is already gone (B4 was a move), so the ApplicationSet prunes the old
  Application and source-ns workload. Source PVCs/PVs (`Retain`) and the source logical DB
  (`Orphan`) remain as rollback until explicitly reclaimed.
- Re-attribute the console `resource_snapshots` row for the DB (the discovery mirror)
  `project_id/environment_id` -> target, if such a row exists.
- Only after a healthy soak: delete the source RWO PVCs and their retained PVs, and remove
  the safety dumps per retention. This is the sole genuinely destructive step and is a
  separate, explicitly-gated runbook action — not part of the move itself.

### Per-app sequences

- **telemost-bot -> internal** (DB-only): B1 -> B3 -> B4 -> B5 -> B6. Near-zero downtime;
  both namespaces reach the same DB during cutover.
- **n8n -> platform** (DB + 2 volumes): B1 -> B2 -> B3 -> B4 -> B5 -> B6. Brief scale-to-0
  window for the consistent volume snapshot.

### Idempotency + rollback

- Each block checks current state and is safe to re-run. Abort before B4 leaves the source
  fully live (delete the partial target render, scale the source workload back up).
- After B4, drive forward (re-run finishes). Rollback after B4 = move the folder back +
  re-point `spec.namespace` back + scale source up; source data never left (Retain PVs +
  Orphan DB + safety dump).

## Part 2 — productize into MoveApp Phase 2/3 (dada-managed Apps)

Do this only after Part 1's real moves succeed, so the code encodes a proven procedure.
Revise `docs/adr/ADR-014-move-app-across-projects.md` Phase 2/3 to the re-point reality
(the current ADR text — "PV rebind by clearing claimRef", "DB data does not live in a
namespace / just re-render the CR" — is partly wrong: the DB is a shared-server logical DB,
and the owner chose copy-to-RWX over claimRef surgery).

### Phase 3 — attached DB (LOW risk; ship first)

In `gitops-agent/internal/worker/move_app.go` `doMoveApp`, stop hard-blocking an attached
ServiceDatabaseV2. Instead:
- Enqueue a safety `CreateDBBackup` for the DB and wait for `Ready` before mutating git.
- Re-render the DB CR under the **destination** app's `resources.values.yaml` with
  `spec.namespace = dstNamespace` and dst project/env labels (reuse the existing
  `resources.values.yaml` upsert path; today the move calls `rv.RemoveKind("ServiceDatabaseV2")`
  at `move_app.go:182` — replace that strip with a re-render).
- Repoint the DB snapshot row(s) via the existing `repointMovedAppSnapshots` path
  (`AppMoveSnapshots` already returns the DB child).
- Env vars: none needed — the connection endpoint is the shared FQDN, namespace-independent.
- Backend `computeMoveImpact` (`backend/internal/api/move_app.go`): reclassify an attached
  ServiceDatabaseV2 from `blocker` to a movable item labeled "database will be re-pointed
  (a safety backup is taken first)".

### Phase 2 — persistent volume (HIGHER risk; flag-gated)

For the dada single-volume model (RWX, Retain), implement copy-into-fresh-volume (matching
Part 1, not claimRef surgery):
- Scale src workload to 0; Longhorn snapshot -> backup -> restore into a fresh volume;
  materialize the dst PVC; verify Bound + data; bring dst up; verify; prune src PVC after a
  soak.
- Feature flag defaulting OFF; a `--dry-run` / MoveImpact preview that prints the exact
  volume/PVC plan without executing; the move stays blocked on volume unless the flag is on.
- `computeMoveImpact`: volume becomes "movable (data copy, brief downtime)" only when the
  flag is enabled; otherwise remains a blocker with the Phase 2 reason.

Keep the owning-app link predicate identical across its ≥4 call sites
(`db/snapshots.go` `AppMoveSnapshots`, `doDeleteApp` cascade, `ListGCChildSnapshots`,
backend `consoleImpact`) — any change to what counts as a child must land in all of them.

## Tests

- **gitops-agent unit (golden-file):** DB CR re-rendered with dst namespace + dst labels
  (not stripped); snapshot repoint including the DB child; the volume-copy planner emits the
  correct Longhorn snapshot/backup/restore + dst PVC (RWX) plan; idempotent re-run is a
  no-op.
- **backend unit:** `computeMoveImpact` reclassifies DB as movable (re-point) and gates
  volume behind the flag; move stays blocked on volume when the flag is off.
- **`dbmove --dry-run`:** golden output of every planned mutation for both real moves;
  executes nothing.
- **Non-prod rehearsal (pre-prod gate):** in a throwaway namespace, create a
  ServiceDatabaseV2 + an RWO PVC with sentinel rows/files, run the full runbook (incl. the
  RWO->RWX copy), and assert data + DB integrity end-to-end. Must pass before touching
  n8n/telemost.
- House rules: no inline `//` comments in Go (doc-comments only); `go build/vet/test ./...`
  green in backend + gitops-agent; swagger coverage gate if any route changes; frontend
  `tsc --noEmit` + build if the move modal copy changes.

## Execution of the real moves (autonomous once tested, evidence-gated)

Order: `dbmove --dry-run` -> non-prod rehearsal -> **telemost-bot** (no volume; lowest
risk) -> soak/verify -> **n8n**. Post evidence at each verify gate: dump size, `select 1`,
row counts, target PVC Bound + `sha256` manifest match, pods Ready, domain 200. Source
DB/PVs/dump retained through the soak; the destructive reclaim (B6 final) is a separate
explicit action after a healthy soak.
