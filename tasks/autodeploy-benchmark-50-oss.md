# Бенчмарк автоподнимателя: 50 открытых проектов

**Статус:** бэклог, не начато. Заведено по ходу работы над каталогом готовых
проектов (`backend/internal/solutions`) — и после того, как каталог поехал
на сборку из исходников, это уже не смежная задача, а обратная связь для
механизма, который стоит на пустом экране у каждого нового пользователя.

**Зачем.** Автоопределение (`backend/internal/sourcedetect` + пайплайн сборки в
`build-agent`) сегодня проверяется тремя нашими же стартерами, которые написаны
так, чтобы оно сработало. Это не проверка, это тавтология: стартер на Next.js
доказывает, что мы умеем поднимать наш стартер на Next.js. Настоящие открытые
проекты писались без оглядки на нас — монорепы, Dockerfile не в корне, сборка в
два шага, порт из переменной окружения, миграции на старте, статика из
подкаталога. Ровно там автоподниматель и ломается, и ровно этого мы про него
сейчас не знаем.

**Что это даёт продукту.** Каталог готовых проектов (карточки на пустом проекте)
и поле «вставьте ссылку на репозиторий» обе идут через автоопределение и нашу
сборку. То есть процент успеха автоподнимателя на чужих репозиториях — это
теперь напрямую процент успеха первого экрана: пользователь, у которого не
собралось, видит не «проект сложный», а «платформа не смогла».

Из этого следуют две вещи. Первая: у нас нет числа, которым мы этот экран
описываем, — бенчмарк его даёт. Вторая: каталог сегодня состоит из четырёх
проектов, у каждого из которых Dockerfile в корне, потому что это форма, в
которой мы уверены; расширять каталог до «крутых проектов» без разбора можно
ровно настолько, насколько бенчмарк показывает, что мы вытягиваем монорепы,
сборку в подкаталоге и порт из переменной окружения.

## Корпус

50 репозиториев, отбор по правилам, а не по вкусу:

- **Открытая лицензия** и живой апстрим (коммит за последние 12 месяцев).
- **Разнообразие по стеку**, а не 40 нодовых проектов: node/next/nuxt/vite,
  python (django/fastapi/flask), go, ruby on rails, php (laravel/symfony),
  java/spring, rust, elixir, статика.
- **Разнообразие по форме репозитория**, потому что именно она ломает
  определение: корневой Dockerfile, docker-compose без Dockerfile, монорепа с
  `apps/*`, приложение в подкаталоге, сборка через Makefile, готовый
  `Procfile`, вообще никаких манифестов кроме `package.json`.
- **Ограничение размера:** один веб-процесс, который может подняться без
  внешней БД или с одной managed-БД, которую мы умеем выдать. Проект,
  требующий Kafka и три очереди, в корпус не идёт — он мерит не то.
- Фиксируется **коммит**, а не ветка: бенчмарк без пинов перестаёт быть
  сравнимым между запусками.

Корпус живёт файлом в репозитории (`tasks/autodeploy-corpus.yaml`,
`repo + commit + ожидаемый фреймворк + ожидаемый порт + чем считать «живой»`),
чтобы результат прогона можно было сравнить с предыдущим построчно.

## Что меряем

Одна попытка = один репозиторий, прогнанный ровно тем путём, которым идёт
пользователь (link repo → build → deploy), без ручных правок. Итог попытки —
одна из четырёх ступеней, и важны все четыре, а не только последняя:

1. **Определился** — `sourcedetect` вернул фреймворк и порт (и оба верные;
   верный фреймворк с неверным портом — это провал, приложение поднимется и
   будет отдавать 502).
2. **Собралось** — билд дошёл до образа.
3. **Поднялось** — под перешёл в Ready и пережил 5 минут (не CrashLoop).
4. **Отвечает** — HTTP 2xx/3xx на `/` по выданному домену.

Метрика, которую мы называем «процентом успеха», — это ступень 4. Ступени 1–3
нужны, чтобы провал был диагнозом: «не определили» и «определили, но не
собралось» — это два разных бэклога.

Дополнительно по каждой попытке пишем: время до ступени 4, размер образа,
пиковую память пода (иначе «поднялось» на 4 ГБ выглядит как успех до первого
счёта) и причину провала из фиксированного словаря (`no_manifest`,
`wrong_port`, `build_oom`, `missing_env`, `needs_db`, `needs_migration`,
`monorepo_root`, `non_http`, …). Свободный текст в причинах — то, из-за чего
следующий прогон нельзя будет сравнить с этим.

## Как гонять

- В песочнице (`agent-sandbox`, правило из `CLAUDE.md`), одним приложением на
  попытку, с уборкой за собой; параллелизм ограничен ёмкостью кластера.
- Прогон — скрипт в `scripts/` поверх публичного API (link repo → trigger build
  → poll operation → probe URL → delete app), без доступа к внутренностям: он
  меряет продукт, а не наши представления о нём.
- Отчёт — таблица «репозиторий × ступень × причина» плюс сводка. Кладётся
  рядом с корпусом, коммитится: два прогона на разных версиях билдера должны
  сравниваться `git diff`-ом.
- Порог, ниже которого каталог не расширяется за пределы проектов с корневым
  Dockerfile: **ступень 4 на ≥ 80 % корпуса**, и ни одного молчаливого провала
  (каждый провал имеет причину из словаря).
