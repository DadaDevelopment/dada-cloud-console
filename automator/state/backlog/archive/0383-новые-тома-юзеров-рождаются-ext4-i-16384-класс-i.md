Заземление [live 2026-08-19/20]:
- SC `longhorn-dev` (дефолт для аппов, `backend/internal/api/apps.go:590`) — `fsType: ext4`, **без `mkfsParams`**; так же `longhorn-prod`, `longhorn-stateful-prod`. Ни один SC в кластере не использует xfs и ни один не задаёт `mkfsParams` (`kubectl get sc -o json | grep -i 'xfs\|mkfsParams'` → пусто).
- Значит mkfs идёт с дефолтом `-i 16384`: 20Gi → ровно 1310720 inode. `tune2fs -l` тома `fonbet-value`: `Inode count 1310720`, `Free inodes 0`.
- Профиль реального юзера: `raw_data/manifests` = 989211 записей на 3.9G (~4 КБ на файл) — то есть 75% inode на 26% байт. При плотности 1 inode / 16 КБ такой аппу гарантированно упирается в inode задолго до байтов.

Работа: задать плотность inode для пользовательских томов. Longhorn v1.6.1 понимает `mkfsParams` (строка есть в бинаре longhorn-manager, проверено `grep -a -c` в поде csi-plugin), а также `fsType: xfs` (inode динамические — класс умирает совсем).
Развилка, решать с уликами, а не на вкус:
- `mkfsParams: "-i 8192"` — тот же ext4, +3% под таблицу inode, вдвое больше inode. Низкий риск, не убивает класс, только отодвигает.
- `fsType: xfs` — inode динамические, класс исчезает. Риск: xfs требует тома >= 300 МБ, а наш регексп размера (`apps.go:591`) разрешает `1Mi`; нужен нижний порог, иначе мелкие тома перестанут провижениться.

Ограничение доставки: SC управляется Argo из mgmt-кластера (`tracking-id: storage-class-longhorn-beget-beget`, `sync-options: Replace=true,Force=true`), в локальном `argo-infra` (ветка console-migration) манифеста нет — сначала найти репозиторий-источник.
M2: в песочнице создать апп с томом → `df -T`/`df -i` внутри пода показывают новую плотность или xfs; существующие тома не тронуты.
